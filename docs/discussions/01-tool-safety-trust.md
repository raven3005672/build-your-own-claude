## 议题 ① 可逆性分级：工具的信任等级 ∝ 不可逆性

### 1. "不可逆"拆成三个维度

| 维度 | 问题 | 例子 |
|---|---|---|
| **能否撤销** | 后果发生后再怎么挽回？ | 覆盖文件 vs 删除文件 |
| **爆炸半径** | 一次调用最多能碰多大范围？ | 一个文件 vs 整个磁盘 vs 外网 |
| **能否先验判断** | 执行前你能界定它干什么吗？ | `Read(a.txt)` 能 vs `bash -c "任意程序"` 不能 |

三者合起来对应安全领域经典的 **CIA 三联**：Read 威胁**机密性**、Write 威胁**完整性**、Bash 三者全威胁（还能打**可用性**）。

### 2. 反直觉的修正：Read 也能不可逆

"只读无副作用"不总成立：

```
Read("~/.ssh/id_rsa")    读进对话 = 数据离开你的机器
Read(".env")             进入 messages → 发给 API → 可能被缓存/记录
```

**信息一旦出墙就收不回来**——读密钥和删文件是同一级的不可逆。这就是为什么生产 harness 的敏感路径（`~/.ssh`、`~/.aws`、`.env`）是**连读都 deny** 的。

### 3. 风险阶梯

| 级别 | 例子 | 后果 | 有撤销层时 |
|---|---|---|---|
| **L0 无副作用** | 读项目内代码、`ls` | 无 | — |
| **L1 不可逆的信息流** | 读密钥、读外部数据进对话 | 泄露无法追回 | 无解，只能事前拦 |
| **L2 可逆写** | 写 git 工作区内的文件 | 可 `git checkout` | 降为 L0 级 |
| **L3 不可逆写** | 覆盖 `~/.zshrc`、删数据库、改远端 | 数据永久丢失 | 有备份则降级 |
| **L4 任意执行** | bash | 以上全部 + 外网 + 装后门 | 只有沙箱能圈住 |

### 4. 控制手段不是"更多"，是"不同性质"

| 手段 | 性质 | 能对付 |
|---|---|---|
| 软边界（代码检查） | 用户态、可被绕过 | 已知形状的风险（路径越界） |
| 人的确认 | 带外、慢但不被骗 | 低频、不可逆的决定 |
| 硬边界（沙箱） | 内核强制、不可绕过 | **不可预测**的风险（见议题②） |
| 撤销层（git/备份） | 事后补救 | 把不可逆变成可逆——**改写整个分级** |

**撤销层直接改变工具的等级**：同一个 Write，在 git 仓库里是 L2（`git checkout` 可回滚），在 `~/.ssh/` 里是 L3。**工具的风险不是固有属性，是"工具 × 环境"的属性。**

### 5. 用户自己的 `settings.json` 就是一份分级实现

```jsonc
"defaultMode": "acceptEdits",          // 文件编辑免确认 —— 工作区在 git 里（L2 + 撤销层 = 降级）
"allow": [..., "Bash(*)"],             // L4 全放行
"deny": [
  "Bash(rm -rf *)",                    // 大规模不可逆删除
  "Bash(sudo *)",                      // 提权 = 突破一切边界
  "Bash(curl * | bash)",               // 远程代码直接执行 = 最大不可预测性
  "Bash(git push --force *)"           // 重写远端历史 = 对别人也不可逆
]
```

设计思路是"宽放行 + 只 deny 最高不可逆性的图案"——实用，但 **denylist 是软边界**：`rm -fr`、`find -delete`、`python -c "shutil.rmtree(...)"`、`git push -f` 都能绕过。这正是议题②的主题。

### 小结

```
权限 = f(不可逆性, 爆炸半径, 可预测性)
撤销层可以改写这个函数
```

**分级的意义不是给工具贴标签，而是决定"用什么性质的手段"**：能圈住的用软边界，圈不住的用硬边界，无法预测的只能靠沙箱 + 人确认；而"能撤销"永远比"能禁止"更实用。

## 议题 ② 软边界 vs 硬边界：为什么"测试通过 ≠ 安全"

### 1. 一句话判据

> **被约束方能不能绕过它？**

- **软边界**：靠代码逻辑检查（`if (!resolved.startsWith(ROOT)) throw`）——能否生效取决于检查代码本身的正确性
- **硬边界**：靠能力剥夺——进程被内核限制后，**那个能力根本不存在**

### 2. 软边界的四类失效

**a. 自己的 bug**：Stage 5 实录——算了 `resolved` 做检查，却把 `file_path` 传给 `writeFile`（校验 A、使用 B）。

**b. 枚举不全（denylist 的形状问题）**：

```bash
rm -fr x                                           # 参数顺序
find . -name '*.ts' -delete                        # 换个工具
python3 -c "import shutil; shutil.rmtree('src')"   # 换个解释器
```

**不可逆操作是无穷种程序，字符串模式是有限集合。** 有限对无限，必然漏。

**c. 字符串世界 ≠ 文件系统世界**：TOCTOU（检查与使用之间世界变了）；软链（项目内 `innocent.txt -> /etc/passwd` 让 `path.resolve` 检查通过但实际写到外面）；大小写不敏感（macOS APFS）；Unicode 归一化。任何基于字符串的检查都与文件系统真实行为存在系统性 gap。

**d. 执行者即被约束者（最深的一条）**：检查代码和被检查的东西跑在同一权限域，检查失效后没有第二道防线。这就是沙箱必须在内核里的原因——**内核不是"更聪明的检查者"，是另一个权限域**。

### 3. 为什么测试天生测不出安全

- **测试**断言"我知道的行为"——覆盖**已知路径**的集合
- **安全**防御"我不知道的行为"——攻击者在**未知路径**里搜索

```
防守方要证明：∀ 路径 p，后果可接受   ← 必须覆盖一切
攻击方只需找到：∃ 路径 p，后果不可接受 ← 一条就够
```

**这个不对称是结构性的，不是"测试写得不够好"。** LLM-as-sensor 测试还更弱：连恶意输入都不测，只测"模型配合时"的行为，且结果非确定。

测试的正当用途是**回归**——保证"不退化"，不保证"安全"。

### 4. 硬边界为什么能兜住

| | 软边界 | 硬边界 |
|---|---|---|
| 机制 | 比较字符串、判断条件 | 系统调用被拒绝（EPERM） |
| 失效条件 | 逻辑有 bug / 枚举不全 / 世界变了 | 内核被攻破（几乎不发生） |
| 依赖被约束方配合吗 | 不配合就绕过 | **不依赖任何东西** |
| 例子 | `startsWith` 检查 | Seatbelt（macOS）/ bubblewrap+Landlock+seccomp（Linux） |

进程可以被完全控制（注入 100%），坏事**依然干不成**——因为拒绝发生在内核，不在进程内。代价：配置复杂、容易过严、跨平台不一致。

### 5. 两层怎么配合

```
软边界（前）：体验层 —— 清晰报错、模型可自我修正；快、便宜
硬边界（后）：保证层 —— 兜底，软边界全挂伤害也有上限
```

类比财务：**审批流程（软）+ 银行账户权限（硬）**。审批单可以伪造，转账权限造不了假。

设计问句：**"如果这一层检查全错了，最坏会怎样？"** 可接受 → 软边界够；不可接受 → 必须有硬边界。

### 6. 回扣用户自己的系统

交易管线上的"守卫"（数据新鲜度、缺失交易日）全是软边界，而且已经用血证明：

`CLAUDE.md` #35 的 `from module import 可变全局名` bug 让 `_expect` 恒为空串，**守卫"从上线起就没生效过"**——没有攻击者、没有报警，保护静默消失。

**软边界最危险的失效方式是"安静地不存在"。** 给守卫加测试的用途是让它别静默失效（回归），不是让它变成保证（那需要结构）。

### 小结

> **检查提高门槛，结构提供保证。**
> 安全的目标不是"让危险操作不可能发生"，而是"让最坏情况可接受"。

生产 agent 产品最终都收敛到"沙箱 + 审批"而不是"更聪明的检查"：没有人能写出覆盖无穷程序的检查器，但人人都能把进程关进笼子。

## 议题 ③ 写工具的设计谱系

### 1. 根问题：`writeFile` 把两件事合并了

原生 `writeFile(path, content)` = **截断重写**——把"改一行"和"整个文件推倒重来"合并成同一个动作。**这是所有麻烦的源头。**

### 2. 六个设计点

**a. 读后写（read-before-write）**：没 Read 过的文件不许 Write（Claude Code 的规矩）。它在防"用模型的记忆覆盖磁盘"——模型整写文件时是在**复现**它记忆中的内容，没读过（或记忆过期）写回去的就是幻觉版本。读后写强制记忆与磁盘至少同步一次。残余问题：读后文件被别人改了 → 更严的做法是写前比对 mtime/hash（乐观并发控制）。

**b. Edit（外科手术式替换）**：`old_string → new_string`，**找不到匹配就报错**（要求唯一匹配）。

| 维度 | Write（整写） | Edit（替换） |
|---|---|---|
| 影响范围 | 整个文件 | 匹配到的那段 |
| 生成成本 | 全文件重打一遍 | 只有改动部分 |
| 出错方式 | **静默**（少打一行没人知道） | **响亮**（匹配不上直接报错） |

**"匹配失败即报错"是故意的**：把"改错了"从静默失败变成显式失败。这是最小权限原则在工具设计上的化身——**想改一行，就给"改一行"的表达能力**。

**c. 原子写（atomic write）**：写临时文件 → rename：

```ts
const tmp = `${target}.tmp-${suffix}`;   // ★ 必须和目标同目录
await writeFile(tmp, data);
await rename(tmp, target);               // 同文件系统内 rename 是原子的
```

防"写到一半被杀留下半截文件"（用户 `CLAUDE.md` #43 的真实风险场景）。要点：rename 的原子性只在**同一文件系统**内成立；再严一点还要 `fsync`（防的是操作系统崩溃）。思路：**不是事后补救，而是让"半完成"这个状态不存在**。

**d. 撤销层：git / 备份**：让不可逆变可逆。实例：Aider 每次 AI 修改后自动 commit，任何修改都能 `git revert`——给 agent 装后悔药，而不是试图禁止它犯错。

**e. 覆盖确认**：`writeFile` 对已存在文件是**无声覆盖**。生产做法：存在性检查 + 展示 diff 让用户确认，或拒绝并要求显式意图。这不是技术问题，是**产品决策**——不可逆操作交给谁拍板。

**f. 路径守卫**：防越界，属于"爆炸半径"维度。

### 3. 放回可逆性框架

| 设计 | 防的是哪一类风险 |
|---|---|
| 路径守卫 | 越界（爆炸半径） |
| 读后写 | 用幻觉覆盖真实 |
| Edit | 大范围误伤 + 静默错误 |
| 原子写 | 半完成状态 |
| 撤销层 | 事后恢复（改写整个分级） |
| 确认 | 低频 + 不可逆的决定 |

### 4. 两条统一原则

1. **工具的表达力应该匹配意图的最小粒度**——想改一行就给"改一行"，想写新文件才是"整写"。超出意图的表达能力，就是风险的藏身处。
2. **让错误响亮，而不是安静**——Edit 匹配失败报错、读后写拒绝盲写、原子写消灭半截状态，同一方向：把"静默损坏"转化为"显式失败"。

更深一层：这些设计的前提都是"**模型是不完美的**"——会幻觉、记忆会过期、会搞错路径。好工具的职责不是假设模型正确，而是**让模型犯错时，后果小且可发现**。与议题②的"最坏情况可接受"是同一件事。

### 5. 回扣用户自己的系统

- `CLAUDE.md` #43 的截断文件风险 = 原子写要解决的场景（实测 0 截断是运气，不是保证）
- #22 的"先备份受影响列" = 撤销层
- "单文件测试再全量" = 缩小爆炸半径

数据管线的三板斧与写工具设计谱系，是同一套理论的两个领域版本。

### 6. Phase 2 钩子

将来给 harness 加工具时，**"Edit 工具 + 读后写规则"是最好的练习**——把这一节的设计亲手实现一遍，比读十篇文档实在。可对照 Aider 的 auto-commit 与 Claude Code 的 Edit 语义。
